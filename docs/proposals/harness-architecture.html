1. TL;DR

One sentence MCP harness wins over document harness exactly when the loop needs live tool integration, multi-actor coordination, or cross-runtime protocol — otherwise document harness (CLAUDE.md / rules / skills) is sufficient and the model absorbs it for free.
Document harness
Static rules, model reads.
MCP harness
Runtime dispatch, protocol-based.
Hooks
Deterministic guards — durable.
ACP / agents
Multi-agent coordination surface.

For the three loops called out in the maintainer's question (validation, interview, research), MCP harness fits where the loop crosses actor boundaries or needs live data; document harness fits when the loop is single-actor reasoning with static context.

2. When MCP harness is most needed

The maintainer's three priority loops have different MCP-fit profiles:

LoopWhat it doesMCP fitReason
Validation loop AI-judge + human-judge agents score artifacts, loop until threshold passes High Multi-actor coordination; needs shared artifact state across judges; tool calls to real APIs to verify (not mock)
Interview loop Agent interviews user / stakeholder to gather context Medium Structured turn-taking fits protocol transport; but single-actor works too if the harness owns the question template
Research loop Fan-out N parallel research agents, dedupe, synthesize High N-actor fan-out, shared deduplication state, external tool calls (web / docs / API) — exactly what MCP transport gives

MCP harness becomes necessary (not just nice-to-have) when any of these is true:

  • Cross-runtime protocol — Claude Code + Codex + future SDKs all speak the same wire protocol. Document harness is per-runtime.
  • Live tool integration — MCP servers (Playwright, Stripe, custom in-house tools) expose live capabilities. Document harness can't dispatch to them.
  • Multi-actor coordination — 3+ agents, structured dispatch, tool-call consensus. Document harness is single-actor.
  • Validation against real data — "test with real API" instead of mock. MCP servers provide real data sources.
  • Persistent context across sessions — MCP state lives in a server. Document harness is session-bound.

If none of the above applies to a given workflow, document harness is the right surface and the model absorbs it for free.

Pick rule of thumb Reach for MCP when the loop crosses actor boundaries or touches external state. Reach for documents when the loop is reasoning over a static corpus. They are complements, not competitors — a healthy harness uses both, with the boundary defined by where state lives (file vs server).

4. Hackathon principles mapped to dev-harness-kit

The maintainer's transcript (the AX Talent War hackathon — 1% acceptance, "context + verification + scaffolding" thesis) maps cleanly onto dev-harness-kit's existing surface.

Context — "재료가 요리를 결정한다"

The agent is already smart. Good context produces good output. dev-harness-kit provides context through:

  • skills/<name>/SKILL.md — structured workflow context per skill
  • rules/ — cross-cutting rules (git-workflow, session-hygiene, skill-authoring, test-files)
  • CLAUDE.md / AGENTS.md — global iron laws and stage state
  • docs/ — deep reference (ACP-DISPATCH, COST-ANALYSIS, ADRs, hook-coverage)

The hackathon's "first prompt is an interview, not a task" maps to /dev-kit:onboard + the interview-loop primitive discussed in §2.

Verification — "Mock 심사위원을 만들다"

Build the judging system before the solution. dev-harness-kit already has this in skeleton form:

  • Deterministic guards (enforcement alpha): hooks/slop-detector.sh, hooks/secret-scan.sh, hooks/tdd-guard.sh, hooks/bash-guard.sh, hooks/worktree-guard.sh, hooks/stop-verify.sh — the "judge is always running" layer
  • Multi-dim review (state alpha): /dev-kit:review, /dev-kit:security, /dev-kit:eval — fan-out to per-dimension agents with adversarial verification
  • Eval-Repair loop: /dev-kit:repair — golden → judge → root-cause → fix → judge → A/B → diff → human-approve. The hackathon's 7-round mock-judge loop is the same shape.

What's missing: the AI-judge / human-judge split as separate skills (the hackathon's "AI judge + human judge = 36 sub-agents" pattern). Adding this is the validation-loop primitive from §2.

Scaffolding — "공통 구조로 병렬 처리"

Same scaffold enables parallelism. dev-harness-kit implements this via:

  • State machine: bootstrap → plan → design → build → review → security → ship — same pipeline regardless of task
  • Worktree-per-task: hooks/worktree-auto-cut.sh + hooks/worktree-guard.sh — physical isolation so parallel agents don't collide
  • Fan-out primitive: tools/parallel_dispatch.py — fan-out + dedupe + verifier + synthesize (closes #177)
  • Shared scaffolding assets: lib/analysis-core, lib/eval_runner.py, lib/render_report_html.py — common engines across skills

The hackathon's "interview template + scoring rubric + hand-off doc, reused across 3 companies" is structurally identical to lib/analysis-core's dimension registry — one definition, many consumers.

Two observations from this map:

  1. Hooks and CLI are the durable surface — they encode deterministic guards and external I/O that next-gen models can't absorb.
  2. Document harness is the absorption target — the model's native context-loading makes CLAUDE.md + rules/ the easiest layer for a model upgrade to subsume. Don't over-invest there.

6. Strategic direction — "models are eating the harness"

The AI Times article (2026-07-09, citing Noam Brown at OpenAI and Logan Kilpatrick at Google): next-gen models will absorb most current harness functionality within months. CLAUDE.md Iron Laws L6 + L7 already anticipate this:

L6: New skills must declare alpha: state|enforcement|analysis. Reasoning-only analysis skills are tolerated only for distinct user intents — minimize new instances.
L7: A skill's alpha is the part the model can't self-impose. Don't spend alpha on reasoning the next-gen model will absorb.

Defensible alpha (the things models can't absorb)

  1. Enforcement hooks — PreToolUse / PostToolUse / Stop hooks short-circuit the model's tool calls. The model can't absorb what prevents it from acting.
  2. State machines — bootstrap → plan → design → build → review → security → ship state with persisted progress across sessions. Format-stuck value.
  3. Cost attribution — /dev-kit:cost-gate reads real provider pricing + USD spend. Real money is the spine that doesn't model-collapse.
  4. External truth — /dev-kit:ci-doctor (live gh API), /dev-kit:cost-gate (real pricing) — what the model can't make up.

Things models WILL absorb

  1. Pure reasoning skills (analysis alpha): inspect, review, prune-propose, docs-maintenance, refactor, prune — collapse into model capability within the next model generation.
  2. Static document harness — model reads CLAUDE.md natively, applies it.

Where MCP harness fits the thesis

MCP harness is a dispatch surface, not a reasoning surface. Dispatch = "where does the tool call go?" = protocol, transport, routing. The model doesn't dispatch; the runtime does. So MCP harness is durable against model improvements — but the surface is small. The four trigger conditions in the original #280 body remain the right adoption guard. Don't over-build.

7. Recommendation

Recommended first move Land a minimal in-process MCP harness as lib/mcp_harness.py with three loop primitives wired in: validation, interview, research. Defer supervisor/sidecar forms until trigger condition 3 (≥ 2 MCP servers) actually fires.

Form: in-process

One Python module loaded by the consumer's runtime. No new process, no IPC, no socket. The trade-off (weak crash isolation) doesn't bite until MCP servers exist — and at that point the boundary question is where the MCP server runs, not whether the dispatcher survives its crash.

Dispatch / transport separation

Keep the dispatch surface (what gets called) separate from the transport (how it gets called). Supervisor/sidecar later swap the transport without re-doing dispatch. This is the seam that matters most.

Use cases — implement first

PrimitiveWhat it doesExisting reuse
Validation loop Dispatch to AI-judge + human-judge agents, collect verdicts, gate the loop on threshold Extend /dev-kit:repair (Eval-Repair loop already has the shape); split judge into judge-ai + judge-human skills
Interview loop Structured agent interviews user / stakeholder; persists answers; hands off to next stage New; reuses /dev-kit:onboard's structured-question surface; emits hand-off/<step>.md
Research loop Dispatch N parallel research agents, dedupe, synthesize Reuses tools/parallel_dispatch.py (fan-out + dedupe + verifier + synthesize)

Lifecycle

  • Global install once — harness lives in dev-harness-kit, not per-worktree
  • Per-worktree enable — hooks/worktree-auto-cut.sh calls mcp-harness.enable
  • Disable — on merge / worktree removal

Boundary with hooks/*

LayerOwns
hooks/* Auth gate, secret scan, slop detector, tdd/bash guard, stop verify, worktree guard
lib/mcp_harness.py Tool dispatch, validation-loop coordination, research fan-out, interview turn-taking

They don't overlap. Hooks are deterministic gates; MCP harness is structured dispatch. The seam is clear: hooks decide whether to allow a tool call; MCP harness decides which tool to call next.
