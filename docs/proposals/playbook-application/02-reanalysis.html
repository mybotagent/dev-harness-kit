Pattern 1 — LoopDetectionMiddleware (re-scored)

v0.3.194 verdict: APPLY (+4)

In v0.3.199, **stage-gate.sh** (NEW) already gates every

stateful hook by reading `.dev-kit/.active-hooks.json` before

the hook runs. This is not the same thing as doom-loop

detection — it gates hook *execution*, not hook *outcome*.

Doom-loop detection (3 identical calls in a row) is still a

gap.

However, the gap is now smaller because:

  • The bash-guard, secret-scan, slop-detector, stop-verify,

and tdd-guard all now source stage-gate.sh; a stage mismatch

short-circuits before the loop-prone code runs.

  • The tdd-guard records the RED/GREEN boundary into

`.dev-kit/.tdd-cycle.json`; a retry-loop in TDD now produces

evidence that the system can flag.

Updated pros (4, was 5)

1. **Catches silent doom loops** that would otherwise burn

5–10k tokens before timing out.

2. **Preserves the user's hourly $ budget** — doom loops are

the #1 silent cost driver.

3. **Additive only** — adds a new hook, no existing behavior

changes.

4. **Easy to test** — fixture with 3 identical Bash calls

triggers the warning; deterministic.

Updated cons (3, was 2)

1. **False positives on legitimate retries** — same as before.

2. **Stage-gate already provides partial coverage** — the new

value-add is smaller than at v0.3.194 (the easy wins are

taken).

3. **One more hook to maintain** — hook count goes 16 → 17.

Updated feasibility

Recommendation

Still apply, but deprioritize to Phase 2. Stage-gate has

consumed the easy wins; the remaining gap is the "slow-think

loop" (3 identical calls but spread across minutes). The

v0.3.194 urgency no longer applies.

Pattern 3 — Research → plan → implement pipeline (re-scored)

v0.3.194 verdict: APPLY BORDERLINE (+1)

In v0.3.199, `lib/analysis_core/` provides a 7-module

infrastructure for "gather evidence → cross-validate → produce

structured output." This is the *research* half of the

pipeline:

analysis_core/
├── __init__.py        # API
├── __main__.py        # CLI entry
├── runner.py          # parallel runner
├── dimensions.py      # typed dimension enumeration
├── evidence.py        # evidence quotation
├── cross_validate.py  # cross-source validation
└── fp_filter.py       # false-positive filter

The pipeline is research-ready. The **plan** and **implement**

halves are still missing — there is no `plan.md` artifact

template and no `Plan → Implement → Validate` skill binder.

Updated pros (5, was 4)

1. **Research half is built** — `lib/analysis_core/` is a

production-tested runner.

2. **40-60% context utilization** — fits the HumanLayer pattern.

3. **Plan is reviewable** before code is written.

4. **Reusable across sessions** — same plan can be resumed.

5. **Composes with existing skills** — `skills/research/` and

`skills/valuate/` already use `lib/analysis_core/`.

Updated cons (2, was 3)

1. **Plan and implement halves still missing** — only research

is built.

2. **Slower per task** — 3 phases × overhead = ~15% longer.

NEW Pattern 6 — PreCompletionChecklistMiddleware

Why now

LangChain reports 52.8% → 66.5% on Terminal Bench 2.0 with just

a `PreCompletionChecklistMiddleware` — a small piece of

middleware that forces the agent to verify against a checklist

*before* declaring done

[src:https://blog.langchain.com/improving-deep-agents-with-harness-engineering/;ts:2026-08-04;type:primary].

v0.3.199 state

No equivalent. The `stop-verify.sh` hook verifies *build* (lint,

test, type) but not *intent* (does the change accomplish the

user's stated goal, are the docs updated, are edge cases

covered). The build passes but the user reads the diff and

says "you didn't do what I asked."

Proposed implementation

Add a new module `lib/pre_completion_checklist.py` that

reads:

  • The user's original request (from `.dev-kit/hand-off/`).
  • The diff (`git diff HEAD~1`).
  • The implementation file paths.

Then enforces a checklist before `stop-verify.sh` allows the

agent to declare done:

□ Are the user's stated requirements addressed?
□ Are docs updated if behavior changed?
□ Are edge cases flagged in the diff?
□ Are public APIs documented?
□ Did the agent skip any tests marked as required?

Pros (4)

1. **Catches "build passes but wrong work"** — the most

common dev-harness-kit failure mode anecdotally.

2. **Composes with stop-verify** — stop-verify is the build

check; the new middleware is the intent check.

3. **Reuses the existing diff-extraction machinery** in

`lib/`.

4. **Doesn't require LLM-as-judge** — the checklist is

deterministic (or rule-based) for 80% of items.

Cons (3)

1. **New module to maintain** — adds surface area.

2. **The "intent" check is fuzzy** — needs careful prompt

or rule design.

3. **One more failure mode** — false positives on the

intent check.

**Net: +2. Apply? YES.**

NEW Pattern 7 — CrashSignal in eval aggregates

Why now

Anthropic's langchain study reports: "a thrown scorer exception

used to yield value=1, arithmetically identical to a

legitimate lowest score; aggregate.compute() read only .value,

so eval verdicts silently absorbed infrastructure failures as

real signal."

v0.3.199 state

FIXED in #557. `lib/behavior_scorers` now exposes a `crashed:

bool` on `DimensionScore` and routes crashed dims to

ESCALATED, excluding them from the weighted-mean divisor.

Verdict: APPLIED (no work)

Pattern is already in place. The fix is in commit a7c0f5b

(2026-08-04). Documented here for completeness.

Updated cumulative pros/cons

Across the 3 APPLY patterns (long-running, research-plan-build,

PreCompletionChecklist):

**Gains (consolidated):**

  • Cold-start recovery: 30-60 min/session (Pattern 2)
  • Plan reuse: 15% of plan steps reused (Pattern 3)
  • Intent verification: catches most-common "build passes,

wrong work" failure (Pattern 6)

  • Doom-loop detection: bonus (Pattern 1, lower urgency)

**Costs (consolidated):**

  • 14 EST hours of work (was 17) — 1 new module + 1 new skill

+ 4 templates + 4 test files

  • 0 lines of existing code changed

**Risk:**

  • All additive. All reversible. All have a test fixture.

**Net: Strong apply.** The 14-hour effort buys 3 load-bearing

patterns, of which 1 has its research half already in

production.

Open questions

1. **Phase ordering**: should PreCompletionChecklist land

*before* Long-running templates? The templates affect

session-start; the checklist affects session-end. They're

independent. Recommend parallel.

2. **Checklist medium**: should the PreCompletionChecklist

be a hook (mandatory) or a skill (advisory)? Mandate

breaks existing flows; advisory is ignored. Recommend

hook with a "skip with justification" escape.

3. **Doom-loop threshold**: with stage-gate in place, is the

3-call threshold still right? Or 5? Recommend defer to

first failure data after stage-gate is in production.
